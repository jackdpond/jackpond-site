  - .nojekyll
  - CNAME

That’s the only _quarto.yml change needed. No new render rule, no navbar entry.

3. Making script.js fully client-side

Two server-dependent pieces to replace, everything else in script.js (tree building, arraysMatchTree, traversal animation, progress bar) already runs in the browser untouched.

3a. Replace fetch('/api/daily-word') with a local computation

Port app.py’s get_daily_word() logic into JS, reading the bundled JSON instead of an API response:

async function loadDailyWord() {
    const response = await fetch('./solutions_5.json');   // relative path, same-origin static file
    const solutions = await response.json();

    const today = new Date();
    const dateStr = today.toISOString().slice(0, 10);      // YYYY-MM-DD, UTC

    const wordKeys = Object.keys(solutions);
    const hash = hashString(dateStr);                       // see below — replaces Python's md5
    const wordKey = wordKeys[hash % wordKeys.length];
    const wordSolutions = solutions[wordKey];

    const dayNumber = Math.floor((today - new Date('2024-01-01')) / 86400000) + 1;

    return {
        word: wordKey.split('/')[0],
        anagrams: wordKey.split('/'),
        solutions: wordSolutions,
        date: dateStr,
        day_number: dayNumber,
    };
}

hashString doesn’t need to be MD5 — the original choice of MD5 in app.py was arbitrary (any stable hash works; it just needs to map a date string to the same index every time). The browser’s crypto.subtle doesn’t even support MD5, so pulling in an MD5 implementation just to match the old backend’s exact mapping isn’t worth it — this is a fresh relaunch, and nobody’s “day streak” carries over from the Render-hosted version anyway. A small self-contained hash (e.g. FNV-1a, ~5 lines, no dependency) is enough:

function hashString(s) {
    let h = 0x811c9dc5;
    for (let i = 0; i < s.length; i++) {
        h ^= s.charCodeAt(i);
        h = Math.imul(h, 0x01000193);
    }
    return h >>> 0; // unsigned
}

Everywhere else in script.js that references solutions.solutions, data.word, etc. stays the same — loadDailyWord()’s return shape is unchanged from the old API response.

3b. Testing caveat

fetch('./solutions_5.json') will fail under file:// (browsers block XHR/fetch to local files via CORS). Test with quarto preview (serves the whole site over local HTTP) or python3 -m http.server from inside wordtree/ — not by double-clicking index.html.

4. Persisting discoveredTrees (localStorage)

Currently discoveredTrees is an in-memory Set, wiped on refresh. Add localStorage, namespaced by date so each day’s puzzle has independent progress and old days don’t interfere:

const STORAGE_KEY = `wordtree_progress_${dateStr}`;

function loadProgress() {
    const raw = localStorage.getItem(STORAGE_KEY);
    return raw ? new Set(JSON.parse(raw)) : new Set();
}

function saveProgress(discoveredTrees) {
    localStorage.setItem(STORAGE_KEY, JSON.stringify([...discoveredTrees]));
}
  • On loadDailyWord(), initialize discoveredTrees = loadProgress() instead of new Set(), and call updateProgress() immediately so a returning player sees their prior progress bar state on load (not just after their next successful tree).
  • Call saveProgress(discoveredTrees) right after discoveredTrees.add(treeString) in checkAndAnimateSolution().
  • Optional, cheap, not required: on load, sweep localStorage for other wordtree_progress_* keys and delete ones that aren’t today’s, so the key set doesn’t grow unbounded across days. Low priority since these are tiny strings, but easy to add while touching this code.
