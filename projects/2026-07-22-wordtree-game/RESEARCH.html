WordTree — Research Notes

Source repo: ~/Documents/GitHub/WordTree/WordTree (git history starts with “Reworked README and instructions”, most recent commit baf514c Add Render deployment configuration and daily word system).

These notes document how the existing WordTree repo works — both the offline solver and the live website — as prep for (1) writing the projects-page write-up and (2) rebuilding the site as a static, serverless page for jackpond.com/wordtree.

1. The puzzle, restated precisely

A puzzle instance is a multiset of letters (an anagram group, e.g. abets/beast/betas/beats/baste). The player fills a binary tree — represented as a fixed-size array in heap/level order, index 0 = root, children of i at 2i+1 and 2i+2 — with those letters, one letter per node, using every letter exactly once. A tree is a “solution” if at least 2 of its 4 traversals (breadth-first, pre-order, in-order, post-order) each spell a valid dictionary word, using each word at most once (so the same traversal string can’t count twice).

Points scale with how many of the 4 traversals hit valid, distinct words for a given filled tree (2 is the minimum to count, 3 is a rare bonus).

2. Solving the game: answer_assembly/

This is the offline pipeline that pre-computes every solution for every candidate word, for a given word length. It’s run manually, not at request time.

Tree.py — a small Tree class wrapping a {index: letter} dict with breadth_first(), pre_order(), in_order(), post_order() methods (recursive traversal by heap index) and a pretty_print_tree() ASCII renderer. This looks like an earlier, OOP-flavored take on the same logic that’s reimplemented functionally in wordtreev2.py — the two aren’t wired together (wordtreev2.py doesn’t import Tree), so Tree.py reads as superseded/dead code kept around from an earlier iteration.

pretty_print_tree.py — the standalone (function, not class) version of the ASCII tree renderer, imported by wordtreev2.py’s solve() for CLI debugging output.

wordtreev2.py — the actual solver, run as a script. Pipeline inside if __name__ == "__main__":

  1. assemble(filename, n=2) — reads a word list (one word per line, e.g. resources/words_five.txt), and for every word, brute-force generates all letter permutations (itertools.permutations) and checks which permutations are also in the word list. This groups the word list into anagram sets (e.g. [abets, beast, betas, beats, baste]), keeping only groups with at least n members (--min_combo, default 2 — you need at least 2 real words sharing letters before a tree can possibly have 2 valid traversals). answer_assembly/assembly.json looks like a saved snapshot of this function’s output for word length 4 — it isn’t read back in by any code path, so it’s leftover output from a debug run rather than a cache the pipeline depends on.

  2. get_trees(root=[0], n=0, max=6) — recursively generates every distinct binary tree shape up to max nodes, where a “shape” is a list of heap indices that are occupied (e.g. [0, 1, 2, 4] = root with a left child, that left child’s own left child, and a root-level right child). At each recursion step it branches four ways: add a left child, add a right child, add both, or stop growing that branch — so it enumerates all shapes, not just complete/balanced trees. max is set to 8 in the driver code, i.e. it only considers shapes with up to 8 occupied nodes (matches word lengths 4–8 seen in resources/).

  3. get_solutions(n, words, trees) → for each anagram group, check_word tries every permutation of the letters against every tree shape from step 2, builds the concrete {index: letter} tree via make_tree, and calls check_tree, which runs all 4 traversals and counts how many produce a word that’s in the current anagram group (and hasn’t already been used by another traversal on this same tree). If the count is >= n (2), the tree + its winning traversals get recorded.

    This is doubly brute-force: permutations of letters (len!) × tree shapes (Catalan-ish growth in node count), each combination evaluated in constant time. That’s why it’s a precompute step, not something you’d run per-request — for 5-letter words this is already 120 permutations × (all shapes up to 8 nodes).

  4. solutions2json writes the final { "word1/word2/...": [ {tree: {...}, traversals: {...}}, ... ] } mapping to --output_file — this is exactly the shape of solutions/solutions_4.json … solutions_7.json. (solutions_9.json is present but effectively empty — 2 bytes, i.e. {} — so 9-letter solving was apparently attempted but never completed/found anything, consistent with words_nine.txt / words_nine_first.txt existing but no corresponding solved output.)

There’s also a solve(word, trees=True) CLI mode (--solve <word>) for interactively looking up and pretty-printing the precomputed solutions for a given word — a debugging/exploration tool, not part of the live game.

Net result: solutions/solutions_{4,5,6,7}.json are fully precomputed, static lookup tables from “anagram-group key” → “list of every valid tree + which traversals it satisfies.” The live game never solves anything at runtime — it only ever indexes into these files.

3. The live website: site/ + app.py

Backend (app.py, deployed to Render per Procfile/render.yaml/runtime.txt/requirements.txt): A tiny Flask app with exactly two jobs: - Serve the static files in site/ (send_from_directory). - Serve /api/daily-word: open solutions/solutions_5.json (hardcoded to 5-letter words), pick which anagram-group key to serve today by MD5-hashing the current date string (YYYY-MM-DD) and taking it mod the number of keys. This is what makes the puzzle deterministic-but-pseudorandom and shared across all players on a given day, à la Wordle. day_number is just a day-count since 2024-01-01 for display (“WordTree #N”). /api/random-word is kept as a “legacy” alias that actually returns the same deterministic daily word (not a random one, despite the name/history — see site/server.py below for what an actual random version looked like).

So: the only real server-side logic is “hash today’s date → pick one of 315 pre-baked keys out of solutions_5.json.” Everything else (rendering the tree, checking the player’s answer, animating traversals) already happens client-side in script.js against the JSON blob the server handed it.

site/server.py and site/demo_server.py are older/alternate entry points, not used by the deployed app (Procfile points at app.py): - server.py: same idea as app.py but genuinely random (random.choice) rather than date-seeded, and only exposes /api/random-word. Looks like the pre-“daily puzzle” version. - demo_server.py: serves a single fixed puzzle from site/demo_solution.json — clearly a fixed demo/screenshot rig (matches resources/word_tree_demo.gif in the README). Worth noting: demo_solution.json’s "tree" field is a flat array (index = position), whereas the real solutions_*.json files use a dict keyed by stringified heap index (e.g. "0", "1", "4", "9" — sparse, only occupied nodes). script.js’s arraysMatchTree (for (const idx in treeObj)) works with either shape by accident (both are iterable key→value), but it means demo_server.py’s payload and the production payload aren’t actually interchangeable data — another sign demo_server.py was a one-off rather than a maintained alternate path. - convert_to_lowercase.py is a one-time migration script (walks solutions/*.json and lowercases everything in place) — not part of any runtime path.

Frontend (script.js, index.html, style.css): - On load, fetch('/api/daily-word') → gets {word, anagrams, solutions, date, day_number} and populates the letter bank (sorted alphabetically) from word’s letters. - The tree is a JS array (tree, grown dynamically in powers-of-two-minus-one chunks up to MAX_NODES = 127 for 7 levels) representing the same heap-index scheme as the backend’s solution trees. cursor/findNextViableEmpty walk the player through valid insertion points (a node is “viable” only if its parent is already filled) as they click letters from the bank. - getNodePositions/drawTree compute SVG layout purely from which indices are currently “visible” (filled or the active cursor) — this is why the tree visually grows as you go deeper instead of pre-rendering a fixed 127-node grid. - Once every letter is placed (countFilledLetters() === maxLetters()), checkAndAnimateSolution(): - Iterates solutions.solutions (the full precomputed list for today’s anagram group) and does an exact structural match (arraysMatchTree) between the player’s tree array and each candidate solution’s tree. - If matched: animates each satisfied traversal (getTraversalIndices walks the same pre/in/post/breadth order client-side) node-by-node in green, prints the found word(s), and tracks progress against totalPossibleTrees = solutions.solutions.length (i.e. “how many of the distinct valid trees for today’s word has this player found”). - If not matched: animates all 4 traversals in red just to show the player what their tree actually spells. - discoveredTrees (a Set of the joined tree-array string) is in-memory only — no persistence, so progress resets on reload. There’s no localStorage/cookie use anywhere in script.js.

Key takeaway: the backend does two things — pick today’s word deterministically, and hand over its precomputed solution list. The frontend does everything else (tree building, matching against solutions, animating, scoring) purely in the browser once it has that one JSON payload. The “server” is really just a keyed lookup + a date hash, both of which are trivial to do in JS.

4. Notes toward a serverless rebuild

Given the above, going static is straightforward — nothing about the gameplay requires a backend, only the current deploy structure (Flask serving files + one derived endpoint) does.

  • Bundle the solution data as static assets. Ship solutions_5.json (or whichever lengths you want to support) as a static file under the new site (e.g. assets/wordtree/solutions_5.json) and fetch() it directly from script.js — no Flask route needed to serve it, it’s just a static file like any image.
  • Move the daily-word hash into JS. get_daily_word()’s logic (MD5 the YYYY-MM-DD string, mod by number of keys, look up that key) is a handful of lines. The MD5 choice was arbitrary — any deterministic hash of the date string works (e.g. a small string-hash function, or even Date-seeded PRNG); it doesn’t need to be cryptographic, just stable across clients. This removes the only piece of real “server logic” in app.py.
  • Drop the Render-specific files entirely — Procfile, render.yaml, runtime.txt, requirements.txt, app.py, flask-cors — none of it is needed once there’s no server. server.py/demo_server.py/demo_solution.json/convert_to_lowercase.py are already-dead alternate paths and can be left behind rather than ported.
  • Decide where letter-length variants fit. Only length 5 is wired into the live daily endpoint today, even though solutions_{4,6,7}.json exist and are presumably solved. If the rebuild wants to support multiple lengths (e.g. a length that cycles by day-of-week, or a user-selectable difficulty), that’s a good moment to add it, since it’s now just “pick which static JSON to fetch” rather than a new Flask route.
  • Fits jackpond-site’s existing Quarto setup with zero extra tooling. The parent site (jackpond-site) is already a static Quarto build with no backend of its own (see _quarto.yml), so this is a fully compatible port: drop index.html/script.js/style.css (lightly adapted) plus the chosen solutions_*.json under a wordtree/ path in the built site, and it works as pure static hosting on GitHub Pages alongside the rest — same as the quarto publish gh-pages deploy already in place for the main site. No API route, no CORS config, no Python runtime.
  • Optional improvement while touching this code: persist discoveredTrees (e.g. localStorage keyed by the day’s date) so a page refresh doesn’t wipe progress — today it’s purely in-memory. Not required for the port, but cheap to add since it’s a pure client-side change now.
  • Housekeeping to consider before porting, not required: Tree.py (superseded by the functional version in wordtreev2.py) and answer_assembly/assembly.json (unreferenced debug output) don’t need to come along; solutions_9.json is an empty result and can be dropped or left out of the static bundle.
